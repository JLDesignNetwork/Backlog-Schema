# JLDN Todo Schema Specification

**Author:** Jeff Langdon  
**Schema Standard:** JLDN Document-Bound Task Tracking System  
**Version:** `2608.16.0-as`

This document defines the official specification for the **JLDN Todo Schema**. Designed as an embedded, version-bound task management protocol, this schema structures project tasks directly within Markdown JSON frontmatter (`todo` array).

---

## 1. Architectural Philosophy

The JLDN Todo Schema adheres to five core design principles:

1. **Document-Bound Isolation:** Task lists reside directly in the JSON frontmatter of the target specification file (e.g., `todo-2608.md`). Tasks are strictly local to that versioned document and **CAN NEVER** reference external files or contain todo data for other files.
2. **Phase-Aware Lifecycle Tracking:** Every task progresses through explicit developmental phases using a standardized `[STATE]:[PHASE]` colon-delimited syntax.
3. **Machine-Readable Structure:** Tasks are stored as structured JSON objects, allowing automated scripts, release tools, and LLM coding assistants to parse, execute, and update tasks programmatically.
4. **Empty Array Validity:** The `todo` frontmatter key MUST be a valid JSON array. An empty array (`"todo": []`) is valid and indicates a document with zero active or historical tasks.
5. **Strict JSON Formatting Standard:** Document frontmatter JSON MUST be valid, UTF-8 encoded JSON formatted with exactly 2-space indentation and no tab characters.

---

### 1.1 Storage Architecture & Storage Modes

The JLDN Todo Schema supports two official storage modes:

#### Mode 1: Embedded Inline Frontmatter (Default for Single Files)
Tasks reside directly within the `todo` array in the Markdown document's frontmatter header (`---` block).

#### Mode 2: Companion Dataset Storage Pattern (Recommended for Large Rulesets)
For large documents where inline task arrays would clutter web Markdown previews, tasks are stored in a companion dataset file (`<document-name>.todo.json` or `.todo.yaml`) residing in the same major version directory.

In Mode 2, the primary Markdown document's frontmatter contains lightweight metadata pointers:
```json
---
{
  "metadata": {
    "author": "Jeff Langdon",
    "rulesetName": "Vampire",
    "version": "2608.36.0-as",
    "todo_file": "todo.json",
    "changelog_file": "CHANGELOG.md"
  }
}
---
```

The companion dataset file (`todo.json`) stores the complete task database:
```json
{
  "version": "2608.36.0-as",
  "todo": [
    {
      "id": "TODO-01",
      "section": "## Behavior & Physiology -> Cardiac Hyper-Focus",
      "link": "vampire.md#physical-attributes--speed",
      "title": "Codify Cardiac Hyper-Focus Mechanic",
      "status": "completed",
      "priority": "high",
      "protection": "protected",
      "existed_since": "2608.1.0-s",
      "details": "Detail the mechanical execution of Cardiac Hyper-Focus..."
    }
  ]
}
```

## 2. Task Object Schema Structure

Each task in the `todo` array must be a valid JSON object matching the following structure:

```json
{
  "id": "TODO-01",
  "section": "## Section Name -> Sub-Section",
  "title": "Short Concise Task Title",
  "status": "in-progress:audit",
  "priority": "high",
  "protection": "protected",
  "existed_since": "2608.1.0-s",
  "details": "Detailed description of the mechanical, technical, or architectural work required.",
  "owner": "Agent-Alpha/Jeff",
  "reason": "Explanation required whenever status is blocked or deprecated.",
  "child_of": "TODO-00",
  "prerequisite": "TODO-00.1a",
  "relates_to": "TODO-00"
}
```

### Property Definitions

* **`id` (String, Required):** A unique identifier prefixed with `TODO-` followed by sequential integers (e.g., `TODO-01`). Task IDs MUST be strictly unique within the document `todo` array; duplicate IDs are invalid. Task ID regular expressions MUST support 2 to 4 integer digits (`TODO-\d{2,4}`), guaranteeing scaling up to 9,999 tasks per document.
  * **Single-Letter Sub-Task Parts (`TODO-01.1a`):** Audits or refactors that split a task into sub-items use dot-number-letter part notation (`TODO-01.1a`). Sub-task numerical indexes MUST use unpadded integers (`.1a`, `.2a`, `.10a`). Sub-task parts are strictly limited to single lowercase letters (`TODO-01.1a` through `TODO-01.1z`). Sub-task parts **CANNOT** be split any further (e.g., `TODO-01.1a.1` is prohibited). If sub-task parts exceed `'z'` (26 sub-items), double-lettering is prohibited; a new top-level task (`TODO-XX`) MUST be created with a `"child_of"` key pointing back to the parent task. Ingestion engines MUST resolve parent IDs by stripping the sub-task suffix (`.1a`), mapping directly back to `TODO-01`.
  * **Sub-Task Priority & Active Parent Dynamic Sync Rule:** Sub-tasks and sub-task parts may define their own distinct priorities. The parent task MUST automatically update its `priority` to match the highest priority contained within any of its **active / non-terminal** sub-tasks or sub-task parts adhering to the 4-level priority rank order (`critical` > `high` > `medium` > `low`). When a `critical` sub-task reaches a terminal state (`completed` or `deprecated`), the parent priority automatically de-escalates to match the highest remaining active sub-task priority.
  * **Parent Task Completion Rule:** A parent task `TODO-01` may transition to `completed` once **ALL** child sub-tasks reach a valid terminal state (`completed` or `deprecated`), provided at least one child sub-task was `completed`.
  * **Parent Task Deprecation Cascade Rule:** When a parent task transitions to `deprecated`, ALL active or pending child sub-tasks (`TODO-XX.1a`) MUST automatically cascade to `deprecated` status (specifying `"reason": "Cascaded deprecation from parent task TODO-XX"`). Cascaded deprecations are immutable terminal states. Re-activating a deprecated sub-task is prohibited; reinstating a feature requires creating a new task with `"child_of"` pointing to the new active task ID.
  * **Parent-Child Blocker Propagation Rule:** If any active child sub-task transitions to `blocked`, the parent task MUST also immediately transition to `blocked` (specifying `"reason": "Blocked by child task TODO-XX.1a"`) until the child blocker is resolved.
  * **Numerical Sorting Rule:** Ingestion engines and sorting scripts **MUST** parse task IDs numerically by stripping non-digit characters (`TODO-`), ensuring correct numeric sorting across single, double, triple, and quad-digit scaling (`TODO-01` to `TODO-9999`).
* **`section` (String, Required):** The target document heading or section path affected by the task (e.g., `## Task Lifecycle States Matrix`). MUST be a valid Markdown heading containing a minimum of 5 characters; bare hashes (`"##"`) or whitespace strings are invalid. Hardcoded numerical section prefixes should be omitted from section strings to preserve reference resilience.
* **`title` (String, Required):** A short, imperative title summarizing the task goal (minimum 5 characters; vague titles like `"Fix"` are invalid). MUST be a single-line string.
* **`status` (String, Required):** The current lifecycle state slug formatted as `[STATE]:[PHASE]` (or standard terminal state). MUST be a single-line string.
* **`priority` (String, Required):** **MANDATORY.** Urgency rating specifying task execution order (`"critical"`, `"high"`, `"medium"`, `"low"`). Adheres to a strict 4-level rank order: `critical` (Rank 4) > `high` (Rank 3) > `medium` (Rank 2) > `low` (Rank 1). Task priority is **mutable** and MUST be escalated immediately if an audit or review uncovers critical flaws.
* **`details` (String, Required):** Comprehensive technical description outlining exact requirements, formulas, or rules to implement (minimum 15 characters; generic placeholders like `"tbd"` or `"."` are invalid).
* **`owner` (String, Optional):** The agent, developer, or team member actively working on or claiming the task to prevent multi-agent execution collisions. Single owners use standard strings (e.g. `"Agent-Alpha"`). Pair-programming or joint ownership MUST use forward-slash delimited syntax (e.g. `"Agent-Alpha/Jeff"`).
* **`reason` (String, Conditional):** **Mandatory** if status is `blocked` or `deprecated`; optional otherwise. Details the root cause or blocker.
* **`existed_since` (String, Conditionally Mandatory):** **Mandatory upon task creation.** Identifies the exact version string of the document when the task object was initially created (e.g., `"2608.1.0-s"`). MUST match valid JLDN Generational Versioning tags (`^\d{4}\.\d+\.\d+-(s|as|b|bs|l|ts|z|a)$`). Remains immutable once set.
* **`blocked_since` (String, Conditionally Mandatory):** **Mandatory when status is `blocked`.** Identifies the exact version string of the document when the task transitioned into `blocked` status (e.g., `"2608.5.0-as"`). Cleared if the task recovers back to an active state.
* **`deprecated_since` (String, Conditionally Mandatory):** **Mandatory when status is `deprecated`.** Identifies the exact version string of the document when the task transitioned into `deprecated` status (e.g., `"2608.10.0-as"`). Locked permanently upon deprecation.
* **`protection` (String, Conditionally Mandatory):** **Applicable ONLY to `completed` tasks.** Specifies architectural preservation governance (`"protected"` or `"open"`).
  * **`"protected"` (Mandatory inclusion when protected):** Flags a completed feature/mechanic as a protected system element requiring close watch. Any future task, refactor, or audit that conflicts with a protected item **MUST refactor around it** rather than altering the protected element.
  * **`"open"` (Assumed Default):** If `protection` is omitted on a `completed` task, it is assumed to be `"open"` by default (stable, but open to future mechanical refactoring if higher-level architecture requires it).
* **`child_of` (String, Optional):** Direct parent task ID within the local document that spawned this task (e.g., `"TODO-01"`). Establishes immutable vertical task ancestry and mathematically guarantees a directed acyclic graph (DAG). Self-referential keys (`"child_of": "TODO-01"`) are strictly prohibited. Parent tasks remain immutable when child tasks are created. Target ID MUST exist within the local document frontmatter.
* **`prerequisite` (String, Optional):** Direct prerequisite local task ID (e.g. `"TODO-01.1a"`) that MUST reach ANY valid terminal state (`completed` or `deprecated`) before this task is permitted to transition to `in-progress`. Enables explicit execution gating for parallel agent workflows. Prerequisite chains MUST form a directed acyclic graph (DAG); circular prerequisite dependencies and self-references (`"prerequisite": "TODO-01"`) are strictly prohibited.
* **`relates_to` (String, Optional):** Horizontal correlation key pointing to a related local task ID sharing mechanical or section context (e.g., `"TODO-04"`). Self-references are strictly prohibited. Target ID MUST exist within the local document frontmatter. Cross-document references are strictly prohibited due to document-bound isolation rules.

## 3. Formalized Task Lifecycle States Matrix

Tasks utilize a modular `[STATE]:[PHASE]` colon-delimited syntax across 4 active developmental phases, plus 3 terminal/exception states:

### Distinction Between Review and Audit
* **`review` (Surface Inspection):** Quick inspection focusing on visual presentation, formatting, aesthetic flair, general appeal, and initial readability.
* **`audit` (In-Depth Mechanical Analysis):** Rigorous, semantic, and structural analysis focusing on core mechanics, math balance, edge cases, loopholes, exploits, and system interactions.

---

### The 11-State Task Matrix Table

| Phase / Group | Status Slug | Definition & Usage Guidelines |
| :--- | :---: | :--- |
| **1. Initial Work** | `pending` | **Initial Queued:** Task created; initial drafting or coding has not started. |
| | `in-progress` | **Initial Active:** Task is undergoing initial implementation or writing. |
| **2. Surface Review** | `pending:review` | **Review Queued:** Initial implementation complete; queued for surface presentation/flair review. |
| | `in-progress:review` | **Review Active:** Currently undergoing surface-level formatting and aesthetic review. |
| **3. Deep Mechanical Audit** | `pending:audit` | **Audit Queued:** Draft complete; queued for deep semantic, mechanical, and edge-case auditing. |
| | `in-progress:audit` | **Audit Active:** Red Team auditing or mechanical loophole analysis is actively underway. |
| **4. Architectural Refactoring** | `pending:refactor` | **Refactor Queued:** Flagged after review/audit for structural cleanup, re-balancing, or code refactoring. |
| | `in-progress:refactor` | **Refactor Active:** Active refactoring or mechanical re-balancing is currently underway. |
| **5. Control & Terminal** | `completed` | **Done & Verified (Immutable):** Task is fully finished, passed all audits, and locked. Re-opening is prohibited. |
| | `blocked` | **Stuck:** Work cannot proceed due to external dependencies or missing user decisions. |
| | `deprecated` | **Obsolete:** Task was cancelled or rendered unnecessary by higher-level design changes. |

## 4. Status, Priority, Protection, and ID Validation Regular Expressions

Automated ingestion tools and CI/CD pipelines validate task status, priority, protection, and ID values against the following regular expressions. Ingestion engines MUST trim leading and trailing whitespace from string properties (`status`, `priority`, `protection`, `id`) prior to regex and schema evaluation. Ingestion engines SHOULD support snake_case keys (`existed_since`, `blocked_since`, `deprecated_since`) as canonical, while tolerating hyphenated key aliases (`existed-since`, `blocked-since`, `deprecated-since`).

### Status Validation Regex
```regex
^(pending|in-progress|pending:review|in-progress:review|pending:audit|in-progress:audit|pending:refactor|in-progress:refactor|completed|blocked|deprecated)$
```

### Priority Validation Regex & Formal Rank Hierarchy
```regex
^(critical|high|medium|low)$
```
* **Rank 4:** `critical`
* **Rank 3:** `high`
* **Rank 2:** `medium`
* **Rank 1:** `low`

### Protection Validation Regex
```regex
^(protected|open)$
```

### ID Validation Regex
```regex
^TODO-\d{2,4}(\.\d+[a-z])?$
```

## 5. Workflow State Transitions & Pathways

```
                               ┌────────────────────────────────────────────────┐
                               │             Unblock Recovery Path              │
                               ▼                                                │
 [ pending ] ───► [ in-progress ] ───► [ pending:review ] ───► [ in-progress:review ]
       │                │                                                       │
       │                │ (Trivial Fast-Track)                                  ▼
       │                ├──────────────────────────────────────► [ pending:audit ]
       │                │                                               │
       ▼                ▼                                               ▼
 [ deprecated ] ◄─── [ blocked ] ◄─── [ in-progress:refactor ] ◄─── [ in-progress:audit ]
                       │                        │                       │
                       └────────────────────────┼───────────────────────┘
                                                ▼
                                    [ completed (Immutable) ]
                                                │
                                                ▼ (Optional "protection": "protected")
                                     Locked System Element
                                     (Must refactor around)
```

### Transition Policy Guidelines

1. **Trivial Fast-Track Pathway:** Simple, non-structural edits (fixing typos, formatting tweaks, date updates) may transition directly from `in-progress` to `completed`, bypassing review and audit loops.
2. **Complex Audit Pathway:** Structural changes (rule mechanics, mathematical formulas, schema definitions, security protocols) **MUST** pass through `pending:audit` or `pending:review` before transitioning to `completed`.
3. **Prerequisite Gating Rule:** If a task specifies a `"prerequisite"` ID (e.g. `"prerequisite": "TODO-01.1a"`), it CANNOT transition to `in-progress` until the specified prerequisite task has reached ANY valid terminal state (`completed` or `deprecated`).
4. **Unblock Recovery Pathway:** A task in `blocked` status recovers immediately back to its previous active state (`in-progress`, `in-progress:review`, `in-progress:audit`, or `in-progress:refactor`) as soon as the blocking dependency or decision is resolved. `blocked_since` is cleared upon recovery.
5. **Immutable Completion & Relational Linking:** Completed tasks are locked, immutable historical records. Re-opening a `completed` task is strictly prohibited. Any new work or bug fix targeting a completed feature requires creating a new local task containing a `"child_of"` property referencing the original parent task ID.
