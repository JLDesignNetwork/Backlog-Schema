# JLDN Todo Schema Specification

**Author:** Jeff Langdon  
**Schema Standard:** JLDN Document-Bound Task Tracking System  
**Version:** `2608.1.0-s`

This document defines the official specification for the **JLDN Todo Schema**. Designed as an embedded, version-bound task management protocol, this schema structures project tasks directly within Markdown JSON frontmatter (`todo` array).

---

## 1. Architectural Philosophy

The JLDN Todo Schema adheres to three core design principles:

1. **Document-Bound Isolation:** Task lists reside directly in the JSON frontmatter of the target specification file (e.g., `todo-2608.md`). Tasks remain tied strictly to that versioned document, preventing task pollution across multiple concurrent production versions.
2. **Deterministic Lifecycle Tracking:** Every task progresses through 5 strictly enforced status states.
3. **Machine-Readable Structure:** Tasks are stored as structured JSON objects, allowing automated scripts, release tools, and LLM coding assistants to parse, execute, and update tasks programmatically.

---

## 2. Task Object Schema Structure

Each task in the `todo` array must be a valid JSON object matching the following structure:

```json
{
  "id": "TODO-01",
  "section": "## Section Name -> Sub-Section",
  "title": "Short Concise Task Title",
  "status": "completed",
  "details": "Detailed description of the mechanical, technical, or architectural work required."
}
```

### Property Definitions

* **`id` (String, Required):** A unique, sequential identifier prefixed with `TODO-` (e.g., `TODO-01`, `TODO-02`).
* **`section` (String, Required):** The target document heading or section path affected by the task (e.g., `## 2. Task Lifecycle Stages`).
* **`title` (String, Required):** A short, imperative title summarizing the task goal.
* **`status` (String, Required):** The current lifecycle state (must be one of the 5 formalized stages).
* **`details` (String, Required):** Comprehensive technical description outlining exact requirements, formulas, or rules to implement.

---

## 3. Formalized Task Lifecycle Stages

All tasks must strictly use one of the 5 formalized status values:

| Stage Name | Status Slug | Definition & Usage Guidelines |
| :--- | :---: | :--- |
| **Pending** | `pending` | **Queued:** Initial state for newly created tasks. Work has not yet started. |
| **In-Progress** | `in-progress` | **Active Work:** Task is currently under active development, drafting, or investigation. |
| **Completed** | `completed` | **Done & Verified:** Task work is fully implemented, verified, and locked into the document. |
| **Completed Pending Follow-up** | `completed-pending-follow-up` | **Provisional Pass:** Task work is implemented, but requires secondary audit, red team testing, or user confirmation before final sign-off. |
| **Pending Refactor** | `pending-refactor` | **Flagged for Optimization:** Task was previously completed, but subsequent changes require code/text refactoring, restructuring, or performance tuning. |

---

## 4. Status Validation Regular Expression

Automated ingestion tools and CI/CD pipelines validate task status values against the following regular expression:

```regex
^(pending|in-progress|completed|completed-pending-follow-up|pending-refactor)$
```

---

## 5. Workflow State Transitions

```
 [ pending ] ───► [ in-progress ] ───► [ completed ]
       │                                   │
       │                                   ├───► [ completed-pending-follow-up ]
       │                                   │
       └───► [ pending-refactor ] ◄────────┘
```

1. **Standard Path:** `pending` $\rightarrow$ `in-progress` $\rightarrow$ `completed`.
2. **Review Path:** `completed` $\rightarrow$ `completed-pending-follow-up` (on audit trigger) $\rightarrow$ `completed`.
3. **Refactor Path:** `completed` $\rightarrow$ `pending-refactor` (on breaking change or audit discovery) $\rightarrow$ `in-progress` $\rightarrow$ `completed`.
